Sonata Satark ML Architecture

End-to-End Pipeline for the Random Forest Pre-Audit Risk Score Predictor

The Data Flow Architecture

This pipeline automates the extraction of historical branch data, trains a Random Forest Regressor, and serves predicted risk scores directly back to the Audit Planner module.

1

SQL Feature Extraction

The stored procedure (`SP_BranchRiskScore`) runs daily/monthly, compressing 2.8 million customers into aggregate Branch-level rows.

2

Database Staging

Data is saved into `TBL_ML_TrainingData` (for 10+ months history) and `TBL_ML_CurrentMonth_Features` (for today's live predictions).

3

Python XGBoost Inference

A Python script loads the Current Month features, feeds them into the trained `model.pkl`, and predicts the raw Risk Score.

4

Planner Consumption

Python writes results to `TBL_ML_PredictedValues`. The frontend Audit Planner reads this table to assign Critical/High/Low grades automatically.

Database Schema Overview

The architecture relies on 4 strictly defined tables, available in the `schema.sql` file in this directory.

1. The Training Vault

Table: TBL_ML_TrainingData
Purpose: Stores 10 to 24 months of branch snapshots (approx. 30k-60k rows).
Key Columns: SnapshotDate, BranchID, Historical_Risk_Score (Y), TotalLoans (X1), NPALoans (X2)...

2. The Live Feature Store

Table: TBL_ML_CurrentMonth_Features
Purpose: Stores the exact same X features, but only for the CURRENT snapshot date.
Trigger: Populated via SQL Agent Job before Python prediction script runs.

3. The Prediction Output

Table: TBL_ML_PredictedValues
Purpose: The single source of truth for the Audit Planner UI.
Key Columns: BranchID, Predicted_Risk_Score (e.g. 450), Predicted_Risk_Grade ('HIGH')

4. The Audit Trail

Table: TBL_ML_PredictedValues_History
Purpose: Tracks every prediction made by the model. Crucial for measuring "Model Drift" over time.

The Modeling Choice: Random Forest Regressor

Given the dataset size (~4,700 rows), the Random Forest Regressor is the optimal choice. Tree-based ensemble models natively handle unscaled tabular data, missing values, and non-linear relationships. By utilizing "Bagging" (Bootstrap Aggregating), Random Forests build hundreds of independent decision trees on random subsets of data, making them incredibly resistant to overfitting on smaller datasets compared to boosting algorithms. Explainability is fully maintained via feature importance and SHAP values, ensuring transparency for the auditing board.
